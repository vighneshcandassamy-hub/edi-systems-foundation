# Open investigation environment v0.2

Authorized scope: create a constructed development world with sufficient information paths for unguided inquiry, not certify a historical reconstruction or implement EDI intelligence. Baseline: `1cbf8505444cdfbbe457da57fe61ff1c806759e7`. Preserve the real-source corpus and v0_1 fixture.

The participant receives an objective and generic tool instructions. It chooses searches, questions, measurements, interventions and conclusions. No required hypothesis/rationale, causal graph, relevance labels, investigation sequence or finite policy menu. The source directory describes ordinary holdings, not which source solves the problem.

Four logical components: PARTICIPANT, CONTROLLER, ARCHIVE, WORLD. Offline operator evaluation is a fifth component. Controller and world share one atomic run database, with different logical ownership: controller owns request admission/journal and published evidence; world owns state transitions. Archive is immutable. Operator owns private assumptions and post-run diagnostics. No EDI architecture is changed or new representation family introduced; actual EDI consumer integration is not claimed.

Scope of sufficient information: the constructed world includes observable population, host composition/age/foliage, treatment, direct non-target effects, weather, harvest and human commitments, with both historical records and new measurements. Structured human question topics return frozen source-linked statements; unsupported questions return unavailable. This is bounded inquiry, not arbitrary conversational expertise. Modern real records remain explicitly external context.

One Python process and SQLite transactions implement the broker, journal, scheduled jobs, simulation and publication. The engine is operator-side; no hidden model or future endpoint is provided. Read the public contract and operator model limits before use. Separate runtime isolation is required for a real blind participant; the complete owner repository cannot be mounted into its process.

Requirements and verification allocation are in REQUIREMENTS.json. Cases in verify.py exercise actual HTTP and durable restart, not a model agent. Reviews cover every directed component pair and the complete inquiry/action/publication feedback path. Scientific equivalence, realistic imagery, rich natural-language inquiry, human pilot, frozen comparative scoring and EDI reasoning remain unqualified.
